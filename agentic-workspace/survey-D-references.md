# Agentic workspace UI survey: reference D

Research checked: 2026-11-09 UTC (2026-11-10 Bangkok). This is input to a design document, not a proposed implementation.

## Evidence and confidence

I fetched the public product pages and documentation linked below. “Verified” means the vendor publicly documents the behavior; it does not mean I inspected a current installed build or measured screenshots. No desktop applications were opened for visual inspection. Exact pixel geometry, default pane ratios, animations, and any undocumented empty/loading/error states are **unverified**. Where a source describes only a CLI/TUI or an older/newer feature surface, that boundary is called out. Vendor feature claims are not treated as guarantees about reliability or as product requirements for Onni.

## Distilled patterns for Onni

| Adopt | Why it fits Onni | Avoid or constrain |
| --- | --- | --- |
| A persistent project/task navigator with readable state badges, search/filter and archive/history. Group urgent states (“needs you”, failed, review) so parallel tasks stay findable. | Codex/Claude/Zed/Warp all make thread identity and return paths first-class. Onni already has project-scoped routes and run lifecycle states. | Do not make cloud accounts, remote environments or online sync the assumed home for task history. Onni is local-first. |
| Keep the thread as the task’s narrative and center. Render tool calls as labeled, status-bearing cards; group routine streaks and let the user expand raw input/output when needed. | Zed/Warp show controls beside ongoing work; Onni has normalized `UiEvent` and `ToolCard` already. | Do not turn the thread into an unfiltered terminal log or hide a failed/interrupted tool inside a generic spinner. Preserve status distinctions and errors. |
| Make Changes a real review surface with per-file diffs, line comments and a clear “send these comments back” action. Keep a shared composer across chat/review where possible. | Claude, Codex, Cursor and Conductor connect review comments directly to the owning agent. Onni’s `TaskComposer` already serves Session and Changes. | Do not treat review comments as a global chat message detached from file/line identity. Do not label a finished task “merged” merely because it is done. |
| Treat terminal, file tree, diff, browser preview and task thread as optional task-scoped views. Offer a small number of resizable columns and named reusable layouts, with one obvious default. | Claude and Cursor expose useful composition; Onni already offers 1–3 columns and seven views. | Avoid opening every pane at once or recreating a full IDE chrome with competing navigation. Exact default geometry is a design decision, not established by this survey. |
| In busy sessions support a visible queue and explicit steer/stop semantics; preserve unsent drafts and stable terminal selection. | Zed/Warp queue prompts; OpenCode changelog calls out keeping drafts, focus and terminal selection across failures/transitions. | Avoid ambiguous Enter behavior or silently converting a queued edit into an immediate prompt. Show when/why input will be delivered. |
| Put approvals/questions at the point in the transcript where the blocked action appears. Explain the action and consequence; distinguish one-time, remembered, reject, and informational question states. | Zed/Warp/Claude show decisions in context. Onni’s supported `ask.requested` already has structured choices. | Do not copy an “always allow” toggle as if every backend can honor it. Onni’s `permission.requested` / `.resolved` types are reserved, not an active cross-runner approval feature. Prefer current `ONNI:ASK` behavior until a new contract and dispatch path exist. |
| Represent manager → worker runs as an explicit tree with distinct run title, backend, branch/worktree, status, report, changed files and parent link. Keep small progress summaries in the parent, with navigation to the child thread for detail. | Conductor’s workspace-per-stream and Onni’s dispatched child `RunRecord`s provide a clear ownership model. | Do not merge runner subagents and Onni dispatched child runs into one count. They have different branch, authority and lifecycle semantics. Do not portray a roster as a sandbox. |
| Use keyboard palette search/actions against a known active task, reveal numbered shortcuts, and keep destructive actions behind confirmation. | Onni’s task palette already provides `@` tasks, `>` commands, `#` worktree files, task-scoped commands and stable keybinding rules. Claude/Zed/Warp demonstrate discoverable shortcut references. | Avoid new bare-key shortcuts in text fields, stealing browser/app keys, or a command that commits/deletes/merges on one ambiguous Enter. |
| Surface background completion and “needs you” when the user has moved elsewhere; retain enough status in the sidebar to return without hunting. Make empty states actionable and loading/error states distinct from “no changes”. | Claude/Zed notifications and OpenCode’s failed-tab/unread changelog point to attention management; OpenCode explicitly fixed failures that could look like empty/clean results. | Avoid blank surfaces for a failed load, a misleading empty diff, or an inaccessible hidden approval. This is a pattern recommendation; this survey did not verify each competitor’s every edge state. |

## Onni product constraints the design must respect

1. **Local-first and zero-config.** No account, database or cloud as a precondition. State is local JSON/NDJSON/Markdown. Features are discovered and degrade quietly if a dependency, peer or writable home is missing. Do not make a new required config file or turn a network/cost-expanding capability on by default. See `docs/project-overview.md:11-24, 64-71`; repository rules `AGENTS.md:16-34, 137-138`.
2. **One task, one isolated worktree.** A task’s home is its run and branch (`.ai/onni/worktrees/<runId>`, `onni/<id8>` unless a naming policy selects another branch); branch identity is stored on the run record. Show the branch/worktree tied to the task and do not imply that a UI split is another execution. See `docs/project-overview.md:103-110`, `AGENTS.md:148-151`.
3. **The task ends under user control; nothing merges itself.** Successful runs go to `done` by default; `review` is conditional on the opt-in review gate, and review/finish, PR creation and PR merge are separate user actions. No auto-merge UI should be the default. See `docs/project-overview.md:114-123, 127-176, 269`; `AGENTS.md:115-119`.
4. **Manager/worker is an orchestration hierarchy, not a security boundary.** A manager dispatches child tasks; dispatch checks the roster and children stay within the worker rules. A root may merge locally only with `managerFullAccess`; the tool never pushes. Raw git commands or a top-level HTTP run are not fenced by the roster, so do not promise a sandbox. See `docs/project-overview.md:77-86`, `AGENTS.md:128-136`, `packages/work/src/server/routes/dispatch.ts:24-96`, and `packages/contract/src/dispatch.ts:150-183, 435-452, 601-632`.
5. **Project, run, agent thread and child run are different nouns.** A `/p/:projectId` scope contains routes; `/tasks/:id` is a run task. A worker child has a real separate run/worktree and a report. Runner subagents are tool activity inside a task. Keep the model visible in labels and navigation. See `packages/web/src/routes.tsx:346-429`, `packages/contract/src/runs.ts:279-289`, and `packages/contract/src/dispatch.ts:601-632`.
6. **Use current seams instead of inventing a parallel workspace system.** The route aliases `/tasks/:id`, `/chat`, `/changes`, `/files`, `/graph`, `/commits`, `/preview`, and `/terminal` all resolve to `TaskWorkspaceRoute` with a view selection. `layout-state.ts` defines `ViewId = session | changes | commits | files | browser | graph | terminal`, and `WorkspaceLayout` holds one to three columns. `WorkspaceColumns` already takes `columns`, `renderView`, `headerExtras`, and resize actions. See `packages/web/src/routes.tsx:351-429`, `packages/web/src/routes/task-workspace/task-workspace.tsx:86-92, 164-177`, `packages/web/src/routes/task-workspace/layout-state.ts:30-32, 122-177`, `packages/web/src/routes/task-workspace/workspace-columns.tsx:53-74, 581-603`.
7. **Make interactions accessible and respect the existing keyboard model.** `WorkspaceColumns` uses a focusable ARIA `separator`; `TreePaneResizeHandle` supports drag, arrow keys, Home/End and double-click reset. The task palette is `TaskPalette` and its task scope/`@`, `>`, `#` grammar and reserved keys are designed in the palette spec. See `packages/web/src/routes/task-workspace/workspace-columns.tsx:581-603`, `packages/web/src/routes/task-git/tree-pane-resize.tsx:62-147`, `.ai/specs/2026-10-17-task-palette.md:14-40, 45-63`, `packages/web/src/components/task-palette/task-palette.tsx:77-111`.
8. **Composer and transcript already have typed seams.** `TaskThreadRoute` reduces persisted run history into `SessionTranscript`; `TaskComposer` is shared by Session and Changes and knows queued/running/waiting/continuable delivery. `UiEvent` includes `turn.started`, `turn.completed`, `item.started`, `item.updated`, `item.completed`, `session.ended`, `session.error`, `ask.requested`, plus reserved permission events. `ask.requested` renders as `AskCard`; `thread-state.ts` deliberately ignores permission events for transcript rendering. See `packages/web/src/routes/task-thread/task-thread.tsx:72-83, 145-170`, `packages/web/src/routes/task-thread/session-transcript.tsx:85-102, 231-280`, `packages/web/src/routes/task-thread/task-composer.tsx:27-37, 58-110, 151-185`, `packages/api-client/src/protocol/ui-events.ts:156-212, 222-265`, `packages/web/src/routes/task-thread/thread-state.ts:718-721, 765-768`.
9. **Parallel signals and notifications have a defined transport.** The app mounts one global SSE provider and run notifications at the root; task/global run status streams update the shared query cache. Use existing event subscriptions rather than adding a socket or polling timer per pane. See `packages/web/src/app.tsx:24-50`, `docs/project-overview.md:121-123`, `packages/web/src/api/events.ts:21-27`, `packages/web/src/components/run-notifications.tsx:16-33`.
10. **Keep subagent details honest.** `AgentsDock` summarizes `SubagentSummary` status/activity/tool-call counts; when the parent run is terminal but the subagent event never settled, it marks that row stalled instead of inventing completion. Child tasks are nested separately by `taskTreeRows` in Global Tasks. Preserve this distinction. See `packages/web/src/routes/task-thread/subagent-dock.ts:24-46, 232-262`, `packages/web/src/routes/task-thread/agents-dock.tsx:34-46, 115-139`, `packages/web/src/routes/global-tasks.tsx:803-810`.

## Short report

The leading products converge on a persistent task/session navigator, an agent-centered conversation, optional composable review/terminal/preview panes, contextual diff comments, explicit busy/attention cues, and shortcut/prompt queues for parallel work. The most direct Onni fit is to compose around its existing `TaskWorkspaceRoute`, `WorkspaceColumns`, `TaskComposer`, task palette, and run/dispatch records. The design must keep worktree ownership, local-first defaults, manager/worker hierarchy, supported approval contracts, and human-controlled review/merge visible.
