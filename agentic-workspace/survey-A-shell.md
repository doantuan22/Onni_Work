# Survey A — current web shell

## Scope and confidence

This is a static survey of the current `packages/web/src` implementation for a design discussion. I read the shell, routes, task workspace, palette, state/fetch, token, and test files cited below. No install, build, test, or dev-server command was run. **Verified** means directly present in the cited code. **Design implication** is an inference for a multi-pane agentic chat workspace, not an existing behavior or approved design.

## Findings at a glance

**Verified:** The generic cockpit shell is a desktop sidebar plus one routed main content region, with a mobile navigation bar and drawer. A separate task-scoped workspace already supports saved horizontal layouts of up to three columns. Its panes are views of one run, not independent task/chat sessions. No dedicated resizable-panel package appears in the web package manifest; the inspected sidebar, task-column, Git tree, and terminal drawer splitters are implemented in app code. [app-shell.tsx:258–318](../packages/web/src/components/app-shell.tsx#L258), [layout-state.ts:30–48, 164–219](../packages/web/src/routes/task-workspace/layout-state.ts#L30), [workspace-columns.tsx:64–80, 230–282](../packages/web/src/routes/task-workspace/workspace-columns.tsx#L64), [package.json:15–39](../packages/web/package.json#L15)

**Design implication:** The clearest seam is to promote or generalize the existing task workspace model while deciding separately how the outer shell, navigation, and task context change. A visual grid alone would not provide independent pane state, task ownership, routing, event lifetimes, or persistence.

## Current shell structure

`App` creates a `QueryClient` once per mounted instance and nests `I18nProvider`, root `GlobalEventsProvider`, `ThemeProvider`, `AppearanceProvider`, `BrowserRouter`, `LastLocationController`, `AppShellContainer`, `AppRoutes`, and the toaster. The root event provider is intentionally above routes so one cockpit owns workspace events. [app.tsx:20–75](../packages/web/src/app.tsx#L20)

`AppShellContainer` gathers shell data and slots: health/capabilities, workspace configuration, todos, projects, and scoped run summaries. It chooses multi-project `ProjectGroups` when there is more than one project; otherwise it supplies the flat nav and one project quick list. It mounts `CommandPalette` and `TaskPalette` globally within the shell. [app-shell-container.tsx:54–147, 188–192](../packages/web/src/components/app-shell-container.tsx#L54)

`AppShell` is slot-driven (`children`, nav and task sections, banner, host widget, project group list, and settings action). Its root is a viewport-height flex row. The desktop sidebar sits beside a content grid with four rows: mobile top bar (empty on desktop), banner, scrollable route main, and bottom composer/safe-area placeholder. The generic shell does not add a desktop top bar; task routes render their own run header. The route child is the sole main region and owns vertical scrolling. [app-shell.tsx:51–101, 112–159, 258–318](../packages/web/src/components/app-shell.tsx#L51)

At `md` and wider, `Sidebar` wraps `SidebarContent` in `SidebarFrame`; below `md`, `MobileTopBar` opens a `SidebarDrawer`/Radix Sheet which renders the same content. The mobile header has a menu button and the active navigation title. Settings URLs are `chromeless`: the app sidebar, drawer, and mobile bar are omitted while the route remains in the main grid. [app-shell.tsx:189–232, 320–358, 368–495, 788–817](../packages/web/src/components/app-shell.tsx#L189)

The sidebar content includes brand/project identity, New Task, Add Project, top-level navigation, task quick list or project groups, then footer utilities/settings/theme. Nav items are capability-gated from health and use `aria-current="page"`; active areas use longest segment-aware prefix matching. [app-shell.tsx:368–559, 633](../packages/web/src/components/app-shell.tsx#L368), [nav-items.ts:18–101, 121–137](../packages/web/src/components/nav-items.ts#L18)

## State, data fetching, and live updates

The app makes a single TanStack Query client. Default queries do not poll, stay fresh five minutes, collect after 30 minutes, and do not refetch automatically on focus/reconnect; retries distinguish 4xx from transport failures. SSE/WS events drive freshness; the run index has a deliberate interval only as a disconnect/frozen-tab backstop. [app.tsx:30–39](../packages/web/src/app.tsx#L30), [query-client.ts:5–61](../packages/web/src/api/query-client.ts#L5)

Query keys in `api/queries.ts` are hierarchical and scope-led; query hooks read/cache server data rather than duplicating it in component state. `useHealthSubscription` subscribes at the app root and updates the health cache; `useRuns` / `useRunsIndex` serve run lists; `useProjectRuns(enabled)` can park work for collapsed project groups. [queries.ts:130–195, 905–951, 1007–1089](../packages/web/src/api/queries.ts#L130)

There are two live transport patterns:

1. **Workspace-wide SSE:** `GlobalEventsProvider` owns one `GET /api/workspace/events` `EventSource`; named events include `run`, `run-deleted`, `todos`, `usage`, `ping`, and workspace events such as `project-added`, `project-removed`, `checkout-progress`, `automation-change`, `tracker-changed`. Reconnect triggers cache reconciliation/invalidation; listeners patch/invalidate query data. [global-events.tsx:38–85, 585–592, 742–807, 993–1002](../packages/web/src/api/global-events.tsx#L38)
2. **Demand-driven WebSocket:** `subscribeTopic(topic, listener)` is a shared lazy `/api/v1/ws` singleton. It ref-counts listeners by topic, subscribes once per topic, unsubscribes when the last listener leaves, and closes after no topic is held. Frames are `{type:'subscribe'|'unsubscribe', topic}` and `{type:'event', topic, data}` / `{type:'error', topic?, error}`. `useHealthSubscription` is a root-level consumer; scoped/view hooks subscribe only for their lifetime and return cleanup. [ws.ts:1–28, 141–207](../packages/web/src/api/ws.ts#L1), [queries.ts:905–951](../packages/web/src/api/queries.ts#L905)

A task run has its own `EventSource` at `/api/runs/:id/events`; v1 `run-event` and v2 `ui-event` are separate event names, with run snapshots and pings. The run-event hook is task scoped. [run-events.ts:7–34, 138–163, 344–373](../packages/web/src/api/run-events.ts#L7)

Other hooks follow the same query/subscription lifetime split: e.g. webhook list hooks are project scoped with SSE invalidation, while webhook toast observers bind to the visible project. [hooks/use-webhooks.ts:5–22](../packages/web/src/hooks/use-webhooks.ts#L5), [hooks/use-webhook-toasts.ts:7–17](../packages/web/src/hooks/use-webhook-toasts.ts#L7)

## Reuse versus change for multi-pane agentic chat

### Reusable (verified components/contracts)

- `WorkspaceColumns` and `ColumnDivider` already implement a keyboard/pointer accessible horizontal multi-column surface with narrow-screen single-pane fallback. [workspace-columns.tsx:64–80, 158–282, 508–605](../packages/web/src/routes/task-workspace/workspace-columns.tsx#L64)
- `layout-state.ts` provides normalized widths, reorder/close/change, bounded three-column layouts, deep-link selection, saved named layouts, and working-layout semantics; `useWorkspaceLayouts` persists layout state per run and coalesces writes. [layout-state.ts:164–219, 618–778](../packages/web/src/routes/task-workspace/layout-state.ts#L164), [use-workspace-layouts.ts:96–189, 191–304](../packages/web/src/routes/task-workspace/use-workspace-layouts.ts#L96)
- Existing shell chrome, mobile Sheet, sidebar splitter, palettes, theme/appearance providers, token classes, `Tabs`, `Dialog`, `Sheet`, `Button`, and query hooks provide reusable primitives. [app-shell.tsx:258–358](../packages/web/src/components/app-shell.tsx#L258), [components/ui](../packages/web/src/components/ui)
- The query cache and root SSE/WS bus can support multiple visible panes if each pane's hooks use project/run query keys and unsubscribe when unmounted or hidden. The existing kept-layout policy explicitly avoids retaining browser/terminal surfaces and closes hidden effects/queries/sockets. [task-workspace.tsx:844–904](../packages/web/src/routes/task-workspace/task-workspace.tsx#L844), [ws.ts:1–28](../packages/web/src/api/ws.ts#L1)

### Must be decided/changed (design implications)

- **Pane ownership:** Current `WorkspaceColumn` stores a `ViewId`; every pane is a view of one `run.id`. A multi-task chat surface needs a pane identity that can own a task/run/project and its own session stream, selection, drafts, and actions. Do not assume `layout-state.ts` already models that.
- **Layout scope and persistence:** Current layouts and terminal drawer are per run. If a workspace can hold panes from multiple tasks/projects, define whether layout state is global, per project, per workspace/tab, or per saved named workspace; also define migration from per-run layouts. Current sidebar width is intentionally screen-local, while appearance is workspace-global. [use-workspace-layouts.ts:96–189](../packages/web/src/routes/task-workspace/use-workspace-layouts.ts#L96), [sidebar-width.ts:1–29](../packages/web/src/lib/sidebar-width.ts#L1), [appearance-provider.tsx:49–109](../packages/web/src/components/appearance-provider.tsx#L49)
- **Shell/navigation boundary:** Generic `AppShellMain` is a single route scroller and routes select one surface. Multi-pane task chat could live inside that main; a workspace-wide cockpit may require replacing the route/main relationship and deciding whether sidebar/project groups remain, become collapsible, or give way to task/session navigation. This is a design choice, not current behavior. [app-shell.tsx:112–159, 258–318](../packages/web/src/components/app-shell.tsx#L112), [routes.tsx:342–695](../packages/web/src/routes.tsx#L342)
- **Focus and shortcut ownership:** Existing shell Mod shortcuts, Task Palette, bare task-workspace shortcuts, terminal keyboard input, and per-user bindings can overlap in a pane-rich layout. The design must define which pane is active, which pane receives composer actions, how shortcuts switch panes, and how shortcuts yield to inputs/terminal/dialogs. Current guards and tests are a baseline. [use-command-shortcut.ts:15–65](../packages/web/src/lib/use-command-shortcut.ts#L15), [task-workspace.tsx:436–500](../packages/web/src/routes/task-workspace/task-workspace.tsx#L436)
- **Responsive behavior:** Current task workspace retains columns but exposes one at a time below 1024px; it does not define a stack/overlay/drag-to-select behavior for a multi-task workspace. Decide the mobile model separately from the desktop grid. [workspace-columns.tsx:40–42, 158–227](../packages/web/src/routes/task-workspace/workspace-columns.tsx#L40)
- **Panel generalization:** The four custom splitters (sidebar, task columns, task terminal drawer, task Git tree) have different sizing/storage semantics.
