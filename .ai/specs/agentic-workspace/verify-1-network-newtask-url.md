# Agentic workspace verification: network, New Task, URL

Read-only source audit for the three proposed design claims in [`design.md`](design.md). No install, build, test, or server command was run. “Verified” below means directly visible in current source; recommendations and implications are labeled separately.

## Verdicts

| Claim | Verdict | Short finding |
|---|---|---|
| 2 — Network | **PARTLY** | The per-run EventSource and root workspace SSE exist, and 2-up run panes would imply at least three streams. That misses an optional project webhook SSE; today’s task-workspace columns are views of one run, and the shared WS bus does not carry run transcript events. |
| 3 — New Task | **PARTLY** | `/p/:projectId/new` is a substantial standalone composer and settings route with persistent draft state. A draft pane is feasible, but it is not supported by the current pane/layout model or component state ownership; success currently navigates away to a run. |
| 4 — URL sync | **PARTLY** | The route identifies the run and a view suffix selects a deep-link layout. Once mounted, ordinary view/layout switches are state-only and leave the URL unchanged. The proposed push/replace policy is new behavior, not current behavior. |

## Claim 2 — network and connection budget

### Verified transport map

- The app mounts `GlobalEventsProvider` above all routes and holds one workspace-wide `EventSource` at `/api/v1/workspace/events`; `apiPath` deliberately leaves `/workspace/*` unscoped. The workspace endpoint carries run-summary and workspace invalidation events across projects. It is not a separate per-task-workspace stream. ([`app.tsx:26-28,41-73`](../../../packages/web/src/app.tsx), [`global-events.tsx:61-63,585-592,993-1002`](../../../packages/web/src/api/global-events.tsx), [`project-scope.ts:81-100`](../../../packages/api-client/src/utils/project-scope.ts), [`workspace-events.ts:24-53`](../../../packages/work/src/server/routes/workspace-events.ts))
- Every scoped project route also mounts `ProjectWebhookNotifications`. If webhooks are enabled, its hook opens and closes one project-scoped EventSource at `/api/v1/p/:projectId/webhooks/events`, including while a task workspace is open. ([`routes.tsx:213-220`](../../../packages/web/src/routes.tsx), [`use-webhook-toasts.ts:10-16`](../../../packages/web/src/hooks/use-webhook-toasts.ts), [`use-webhooks.ts:9-22`](../../../packages/web/src/hooks/use-webhooks.ts))
- A rendered `ConversationColumn` calls `useRunHistory(run.id)`. The history hook uses `useRunEvents`, which creates an EventSource for the scoped `/runs/:id/events` URL once history is ready; cleanup closes it. Its named frames include `run-event`, `ui-event`, `run`, and `ping`. There is no hook-level deduplication, so each rendered Chat column opens its own run stream, even when columns show the same run. ([`task-workspace.tsx:646-650,918-940`](../../../packages/web/src/routes/task-workspace/task-workspace.tsx), [`run-history.ts:286-295`](../../../packages/web/src/api/run-history.ts), [`run-events.ts:344-354,418-432`](../../../packages/web/src/api/run-events.ts), [`sse.ts:23-61,94-98`](../../../packages/work/src/server/routes/sse.ts))
- Existing workspace `ViewId`s are views of the task identified by the route, not separate conversations. The pure layout transition permits duplicate views, and its test explicitly permits two `session` columns; layouts cap at three columns. ([`layout-state.ts:30-48,502-510`](../../../packages/web/src/routes/task-workspace/layout-state.ts), [`layout-state.test.ts:233-254`](../../../packages/web/src/routes/task-workspace/layout-state.test.ts))
- There is no fetch-based streaming reader in `packages/web/src` or `packages/api-client/src`; the persistent HTTP streams found are EventSources. Terminal output is cursor-based authenticated HTTP: locally an active terminal session subscribes to a `terminal:<sessionId>` topic for a cursor notification, then reads bytes over HTTP; remote or refused topic subscriptions poll at 400 ms. The terminal drawer separately polls session labels. ([`terminal-pane.tsx:12-24,282-305`](../../../packages/web/src/routes/task-workspace/terminal-pane.tsx), [`client.ts:2789-2835`](../../../packages/web/src/api/client.ts), [`terminal-drawer.tsx:136-160`](../../../packages/web/src/routes/task-workspace/terminal-drawer.tsx))
- Terminal notifications, health, host usage, and tracker watches share one lazy app-wide `/api/v1/ws` WebSocket. The client ref-counts topics over that one socket; terminal bytes do not travel over it. Locally the root health subscription opens the socket after HTTP health confirms local mode; remote mode stays on authenticated HTTP. ([`ws.ts:2-20,55-90,141-181,200-207`](../../../packages/web/src/api/ws.ts), [`queries.ts:890-933`](../../../packages/web/src/api/queries.ts), [`terminal.ts:35-60`](../../../packages/work/src/server/routes/terminal.ts), [`client.ts:2791-2796`](../../../packages/web/src/api/client.ts))
- Runner subagents have no separate network stream. The protocol marks `toolKind: 'task'` as a subagent spawn; the Agents dock derives rows from the reduced parent transcript turns. Those transcript events arrive on the parent run EventSource. ([`ui-events.ts:24-39`](../../../packages/api-client/src/protocol/ui-events.ts), [`subagent-dock.ts:6-18,61-76`](../../../packages/web/src/routes/task-thread/subagent-dock.ts))

### Count and protocol implications

For a desktop task workspace with three active Chat columns, the current worst case is **five EventSources per tab** when project webhooks are enabled: three per-column run streams, the root workspace SSE, and the project webhook SSE. With webhooks disabled it is four. In local mode, add **one physical shared WebSocket**; terminal topic subscriptions reuse it. This is a long-lived transport count, not a count of concurrent finite HTTP requests. (Evidence: `ConversationColumn` and three-column allowance above; webhook observer always mounts for project routes and gates on capability.)

For the proposed two visible run conversations, two per-run streams plus the root stream give three SSEs; an enabled project webhook observer makes the real count four. Today’s existing “2-up” task layout is not two run threads: it can show two or three views of the same run. A 3-Chat layout still opens three duplicate run SSEs because every column independently mounts `useRunHistory`.

The local engine calls Hono’s Node `serve()` and the client source explicitly identifies the local Hono server as HTTP/1.1, with the browser’s roughly six-per-origin HTTP/1.1 connection cap. At five long-lived SSEs in one capability-enabled tab, a second tab can readily queue additional SSE and ordinary requests; two three-Chat tabs request ten SSEs. The server-side app is not an HTTP/2 server. An installed VPS may terminate browser traffic at nginx with HTTP/2 on its TLS listener, so the HTTP/1.1 starvation statement should be scoped to local/direct HTTP/1.1 (and remote proxies without H2). ([`server.ts:50,2285-2333`](../../../packages/work/src/server/server.ts), [`global-events.tsx:585-590`](../../../packages/web/src/api/global-events.tsx), [`keep-alive.ts:10-13`](../../../packages/work/src/server/keep-alive.ts), [`ubuntu-vps.ts:332-349`](../../../packages/work/src/server-install/platforms/ubuntu-vps.ts))

The WS wire format is generic JSON `{type, topic, data}`, and the hub can register dynamic publishers, but the server currently registers `health`, `host`, `tracker:<id>`, and `terminal:<id>` topics only. Subscribing to an unregistered topic returns `unknown topic`; no run transcript publisher/topic exists. So `/api/v1/ws` **could** carry run topics after implementation, but it cannot carry them today. A run-topic publisher would need lifecycle and trust handling; current non-health topics are trusted-only by default. ([`ws.ts:42-68,144-177,228-245`](../../../packages/work/src/server/ws.ts), [`server.ts:1484-1518`](../../../packages/work/src/server/server.ts), [`tracker/watch.ts:19-41`](../../../packages/work/src/server/tracker/watch.ts), [`terminal.ts:49-60`](../../../packages/work/src/server/routes/terminal.ts))

Hidden layout behavior is mixed by surface. Inactive kept layouts render under React `Activity` hidden mode, which cleans up their effects while retaining state; terminal and preview layouts are excluded from the kept set because they own live sockets/pages. At narrow widths, only the selected column is rendered. Within the terminal drawer, background terminal tabs stay mounted but their active guard stops reads/subscriptions. Therefore hidden layouts and tabs do not imply a live per-run or terminal topic for every retained view. ([`task-workspace.tsx:848-903`](../../../packages/web/src/routes/task-workspace/task-workspace.tsx), [`workspace-columns.tsx:158-223`](../../../packages/web/src/routes/task-workspace/workspace-columns.tsx), [`terminal-pane.tsx:22-24,282-305`](../../../packages/web/src/routes/task-workspace/terminal-pane.tsx))

**Recommended correction to the design:** state the current budget as “one app-lifetime workspace SSE, optionally one scoped project webhook SSE, and one EventSource per mounted Chat column; the app has at most one shared WS transport locally, whose current topics do not include run transcripts.” For the target two-run layout, budget three or four SSEs depending on webhooks. Either cap visible per-run SSEs/use HTTP/2 where available, or implement a shared run-event transport; do not describe the existing WS bus as a run-event transport before a run publisher and access policy exist.

## Claim 3 — New Task as a draft pane

### Verified route, state, and submit behavior

- `/p/:projectId/new` renders `NewTaskProjectRoute` → `NewTaskRoute`. Unlike the lazy-loaded `TaskWorkspaceRoute`, `NewTaskRoute` is imported directly by `routes.tsx`. It paints a full-screen new-task hero with the `Composer`, `TaskSummary`, `TaskSettingsPanel`, suggestions, and the run-mode explanation. ([`routes.tsx:1-3,23,60-63,346-348`](../../../packages/web/src/routes.tsx), [`new-task.tsx:169-178,887-900`](../../../packages/web/src/routes/new-task.tsx))
- Form state is not one prompt string: `NewTaskDraft` includes source, backend/model/account, variants, worktree and branch choices, autonomy, limits, dispatch, roster, and other settings. The draft is loaded/written from a module cache plus project-keyed `localStorage`; image attachments are held in a separate in-memory map keyed by project and deliberately are not persisted. The project route is keyed to remount on project changes. ([`new-task-draft.ts:14-69,309-337,352-380`](../../../packages/web/src/routes/new-task-draft.ts), [`new-task.tsx:184-238`](../../../packages/web/src/routes/new-task.tsx), [`routes.tsx:224-238`](../../../packages/web/src/routes.tsx))
- `TaskSettingsPanel` is a shell receiving slot content from `new-task.tsx`; branch/worktree controls form part of its `where` slot. Manager-worker roster editing is nested in `ManagerWorkerPill`, which holds its own `RosterDraft` and renders `RosterEditor`. These are normal draft settings sent with the run request; the composer does not create a run worktree before submission. ([`task-settings-panel.tsx:32-60`](../../../packages/web/src/components/task-settings-panel.tsx), [`new-task.tsx:1054-1070,1174-1239`](../../../packages/web/src/routes/new-task.tsx), [`manager-worker-pill.tsx:36-82,135-139`](../../../packages/web/src/components/manager-worker-pill.tsx), [`new-task.tsx:760-790`](../../../packages/web/src/routes/new-task.tsx))
- Normal submit calls `createRun(body)` and then `navigate(startedRunPath(created))`. The helper selects the first run for a variants response, otherwise its sole run, and routes to `/tasks/:id`; server `POST /runs` returns `201` with a run or `{runs}`. This is a normal push navigation because no `replace` option is passed. Scheduling is a separate branch: it posts a deferred schedule and returns without creating or navigating to a run. ([`new-task.tsx:795-846`](../../../packages/web/src/routes/new-task.tsx), [`new-task-form.ts:476-481`](../../../packages/web/src/routes/new-task-form.ts), [`client.ts:1461-1469`](../../../packages/web/src/api/client.ts), [`runs.ts:400-425,489-498`](../../../packages/work/src/server/routes/runs.ts))

### Draft-pane feasibility and blockers

**Inference:** the form can be hosted as a draft pane after extracting a pane-owned composer surface, but it cannot be dropped into the current `TaskWorkspaceRoute`/`WorkspaceColumns` as-is:

1. The current design’s `PaneRef` requires a `runId`, while `TaskWorkspaceRoute` immediately queries a run id. Existing task layouts serialize columns from the fixed `ViewId` vocabulary; they have no draft view or null-run state. Add a distinct draft/run pane union to the new workspace-level state instead of making an existing saved `WorkspaceLayout` column ambiguously nullable. ([`design.md:76-83`](design.md), [`task-workspace.tsx:92-95,158-168`](../../../packages/web/src/routes/task-workspace/task-workspace.tsx), [`layout-state.ts:30-48,121-129`](../../../packages/web/src/routes/task-workspace/layout-state.ts))
2. Draft state is one-per-project today, not one-per-pane: two New Task panes in the same project would share the same `localStorage` key, memory cache, and attachment map. `ManagerWorkerPill` and panel-open/focus state are also component-local. Key state by a draft/pane id, or enforce one draft pane per project and make that constraint explicit. ([`new-task-draft.ts:309-337,352-380`](../../../packages/web/src/routes/new-task-draft.ts), [`new-task.tsx:432-438`](../../../packages/web/src/routes/new-task.tsx), [`manager-worker-pill.tsx:59-72`](../../../packages/web/src/components/manager-worker-pill.tsx))
3. `NewTaskRoute` depends on route params, project scope, and search params; it captures bookmarklet parameters once and handles launch-key auto-start/URL cleanup. Project switching uses a scoped navigation. A pane needs explicit project/draft identity and a callback for these route-bound behaviors. On successful POST, the current route clears its draft and leaves for `/tasks/:id`; promotion-in-place instead must replace the same pane’s draft reference with the created run reference and coordinate the active-run URL. ([`new-task.tsx:178-199,652-675,843-846,967-990`](../../../packages/web/src/routes/new-task.tsx))
4. Define the schedule outcome separately: it creates a deferred task without a run id, so it cannot follow the same promote-to-run transition. For variants, current behavior promotes/navigates to the first run only; decide whether sibling variants are exposed in the pane model. ([`new-task.tsx:815-820`](../../../packages/web/src/routes/new-task.tsx), [`new-task-form.ts:476-481`](../../../packages/web/src/routes/new-task-form.ts))

**Recommended correction to the design:** define an explicit `DraftPaneRef` (with a `draftId` and project id) alongside `RunPaneRef`; extract a reusable composer surface from `NewTaskRoute` that receives draft identity and `onStarted`/`onScheduled` callbacks. On a successful run POST, update the same pane id to reference the first returned run and then sync the active-run route; keep schedule handling as a separate saved/scheduled outcome. Keep the current per-run saved context layouts on their existing `ViewId` schema.

## Claim 4 — URL and layout synchronization

### Verified current behavior

- The scoped route map contains `/p/:projectId/tasks/:id` and suffix routes for Chat, Changes, Files, Graph, Commits, Preview, and Terminal. `TaskWorkspaceRoute` reads `:id` with `useParams()` and loads that run, so the path is the current active run identifier. A supplied suffix becomes `deepLinkView`. ([`routes.tsx:346-428`](../../../packages/web/src/routes.tsx), [`task-workspace.tsx:92-95,146-166`](../../../packages/web/src/routes/task-workspace/task-workspace.tsx))
- Once layouts are ready, `deepLinkView` causes `openDeepLink()` or selection of a previously minted layout. That is route-to-layout initialization for deep links. Ordinary fixed-view, saved-layout, column, and keyboard switches call `openDeepLink`, `selectLayout`, or other layout-state actions directly; they do not navigate or rewrite the task URL. The selected layout is persisted through `useWorkspaceLayouts(run.id)` and the `/runs/:id/layouts` API. Notes is an exception: it navigates to `/tasks/:id/notes`. ([`task-workspace.tsx:192-234,369-416,441-459`](../../../packages/web/src/routes/task-workspace/task-workspace.tsx), [`use-workspace-layouts.ts:108-170,265-327`](../../../packages/web/src/routes/task-workspace/use-workspace-layouts.ts), [`layout-state.ts:695-716`](../../../packages/web/src/routes/task-workspace/layout-state.ts))
- `TaskWorkspaceRoute` tracks `useNavigationType()`. On a deep link it records the prior layout; on a later `POP` without a deep-link suffix it restores that layout. Its effect deliberately omits `layouts.state.active` so it runs on router navigation rather than reapplying a stale deep-link view after every layout-state change. ([`task-workspace.tsx:192-234`](../../../packages/web/src/routes/task-workspace/task-workspace.tsx))
- Current URL compatibility is tested: scoped route tests assert that a task-tab deep link selects that surface; task workspace tests assert deep-link selection and run-id navigation; layout-state tests cover deep-link idempotence, duplicate columns, and the three-column cap. These constrain a redesign to preserve route/deep-link behavior and the existing task layout model. ([`routes.test.tsx:243-257`](../../../packages/web/src/routes.test.tsx), [`task-workspace.test.tsx:271-289,500-524`](../../../packages/web/src/routes/task-workspace/task-workspace.test.tsx), [`layout-state.test.ts:233-254,470-482,768-782`](../../../packages/web/src/routes/task-workspace/layout-state.test.ts))

**Verdict detail:** URL-as-source-of-truth is already true for the single active `runId`; it is **not** true for the active context view after initial load. The “push run switch / replace subview switch” policy is not current behavior for workspace tabs, because those switches are state-only. Run creation navigates to its new route without `replace`; deep-link path visits remain bookmarkable.

**Loop risk and correction:** If route-to-layout and layout-to-route effects are both added naively, the current `deepLinkView` can re-select an old route view after a local layout change; including `layouts.state.active` in the current effect dependencies would also make that effect rerun on each state transition. Make the route-derived active run/view the single input, compare it to the current effective selection before applying it, and route local actions through a centralized navigation policy. Keep extra panes/splits/layouts in workspace state because one URL cannot represent them all. Preserve `POP` handling deliberately and test that Back/Forward, direct deep links, internal view changes, run switches, and initial async layout loading converge without stale-route reapplication.

**Recommended correction to the design:** phrase the target as “the path identifies the active run and its context view; selecting another run pushes a history entry, selecting a different context subview replaces the current entry; extra open panes and split arrangement stay in workspace state.” Treat this as new behavior to implement and test, not as a description of today’s URL synchronization.
