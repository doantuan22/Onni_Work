# Project Graph: impact, chọn test, phối hợp agent và UX có lực kéo

Ngày chốt số liệu: **2026-11-13**. “Stars / cập nhật” là metadata GitHub đọc trong ngày; ngày cập nhật là `pushed_at` (không đồng nghĩa ngày commit cuối trên nhánh mặc định). Số sao là tín hiệu chú ý, không phải bằng chứng dùng thường xuyên. Bảng phân biệt tài liệu/chứng cứ sản phẩm, nghiên cứu thực nghiệm và tự báo cáo. **chưa kiểm** nghĩa là chưa tìm thấy số đo độc lập có thể đối chiếu, không có nghĩa là công cụ không hữu ích.

Phạm vi này đi tiếp từ [`PLAN.md`](PLAN.md), [`research-engines.md`](research-engines.md) và [`research-viz.md`](research-viz.md): tập trung vào hiệu quả được quan sát, giới hạn khi áp dụng, và điều gì đáng thay đổi trong kế hoạch.

## Kết luận nhanh

- Với **TypeScript monorepo**, lấy package/workspace graph + Git diff + reverse dependents làm mặc định cho “affected”; dùng test runner (`vitest related/--changed`, `jest --findRelatedTests`) như phép chọn bổ sung ở cấp test. Bắt đầu từ metadata/package graph vốn đã có, không cần dựng một máy phân tích tổng quát mới để có giá trị.
- Với **repo tùy ý**, không có graph tĩnh cấp file nào vừa rẻ vừa bảo đảm đủ: ưu tiên lệnh `test/build` do repo khai báo (Nx/Turbo/Rush/Bazel/Pants), rồi dùng import graph/test-runner nếu parser và cấu hình hiện diện. Nếu không biết cách chạy test hoặc dependency resolution mơ hồ, trả “ứng viên” và chạy rộng hơn; không hứa chắc chắn an toàn.
- Import hub không làm impact vô dụng; nó làm **impact không phân biệt**. Hiển thị theo lớp: changed files → import dependents → package/build targets → tests, kèm số lượng, confidence, lý do và mở rộng theo yêu cầu. Hầu hết người dùng cần hành động cụ thể, không cần toàn bộ transitive closure trên một canvas.
- Với worker, worktree riêng chỉ ngăn ghi đè đồng thời. Va chạm thực tế giảm nhờ **một owner cho mỗi vùng/file**, task được tách theo module/API, hợp đồng giao tiếp trước khi chạy, và merge thử sớm. File overlap dễ dự đoán; semantic conflict qua file khác nhau khó hơn. Graph có thể cảnh báo, không thể bảo đảm “không conflict”.
- Lực kéo bền nhất của graph là graph làm đầu vào cho lệnh/action (Nx affected, dependency security, impact của diff), chứ không phải xem bản đồ toàn repo vô thời hạn. Giữ overview như cửa vào, nhưng neo trải nghiệm vào diff, test, worker hoặc node đang xử lý.

**Điều gì thật sự giảm va chạm?** (1) Worktree/branch riêng cô lập filesystem, ngăn agent ghi đè trực tiếp; Git bắt textual overlap ở merge. (2) Scope ownership một-writer-per-file/area chặn trùng từ khâu lập kế hoạch, nhất là file “hot” như config, translations, central types. (3) Tách theo module/API và định nghĩa interface trước, cho phép parallelism mà không cần chung file. (4) Trial merge/rebase hoặc merge queue sớm cho conflict chính xác trên nội dung thực. (5) Co-change và concurrent-edit history chỉ xếp hạng cảnh báo cho các file liên quan, không lock tự động. File-scope lock cứng có thể serialize vô ích khi các edits khác dòng, và vẫn bỏ sót semantic conflict trên file khác nhau.

Số liệu thực nghiệm về hiệu quả “chia disjoint file scope” riêng cho coding agents còn mỏng. AgenticFlict đo xung đột PR, không thử nghiệm policy partition. Bài báo về editing patterns trên ba dự án OSS báo file chỉnh sửa đồng thời bởi nhiều developer có xác suất bug tương lai **1.8×**, cùng nhiều mẫu khác; đây là tương quan, không chứng minh lock ngăn lỗi ([study](https://sailresearch.github.io/sail-website/data/pdfs/2016_AnEmpiricalStudyoftheEffectofFileEditingPatternsonSoftwareQuality.pdf)). Kết luận thực dụng: implement overlap warnings + ownership + speculative integration trước khi gọi “conflict prediction”.

## Trả lời bốn câu hỏi

### 1. Best value per effort: TS monorepo và arbitrary repo

**TS monorepo:** (a) workspace/project package graph; (b) path diff từ Git; (c) reverse dependency closure tới apps/packages; (d) target commands từ package manager/Nx/Turbo/Rush; (e) runner-specific test selection. Nếu TS monorepo dùng Vitest/Jest, gọi native related selection trước khi viết selector khác. Với repo hiện tại của Onni, package boundaries đã rõ và có bốn npm workspaces: việc build task-level impact trên project graph hiện hữu cho MVP có ROI tốt hơn lập classifier ML. File import graph giúp xem đường đi và tăng độ chi tiết, nhưng không thay project graph.

**Arbitrary repos:** nhận biết build system, hỏi chính tool đã có để chọn targets; nếu không có, quét dependency imports ở các ngôn ngữ parser sẵn có và đề xuất “likely affected tests”. Thêm lịch sử test→files từ coverage khi test runner cung cấp sẵn. Không tự tích hợp model predictive kiểu Meta trước khi có dataset đáng kể và telemetry nội bộ (đi ngược local-first nếu cần upload). Không xây bản sao Bazel query. Lệnh fallback an toàn là test rộng hơn thay vì báo “không ảnh hưởng”.

**Cách giảm hub inflation:** tính closure từng edge type riêng; chỉ show N mức hoặc giới hạn kết quả; gom theo workspace/package/folder; phân nhóm exact static import vs build config/global input vs inferred co-change; nêu hub/path gây lan rộng; cho phép click “why”; có bảng candidate thay vì ép canvas. Nếu thay đổi `index.ts`, root config hay generated registry thật sự ảnh hưởng nhiều, kết quả rộng là đúng; nếu chỉ vì barrel re-export làm mọi đường nối nhau, người dùng cần provenance và edge opt-out.

### 2. Điều gì thực sự ngăn agent đụng nhau?

Worktree isolation là **isolation kỹ thuật**, không phải partition: agent có thể sửa cùng file độc lập rồi gặp merge conflict, hoặc sửa file khác nhau tạo contract conflict. Ownership/scope là phương tiện phòng ngừa mạnh nhất; trial merge và test tích hợp là phát hiện/khắc phục. Dùng graph để (1) gợi ý vùng dependency cluster; (2) tính file overlap/nearby common hubs; (3) đưa cảnh báo co-change; (4) yêu cầu manager chọn owner cho shared files; (5) trước dispatch, tạo nhánh/commit thử tích hợp nếu đã có changes; (6) sau mỗi child, rebase/trial merge sớm và chạy tests của vùng giao nhau.

Không thấy nghiên cứu A/B hiện đại chứng minh một file-scope lock tốt hơn ownership conventions cho agent teams. Palantír hỗ trợ workspace awareness trong thí nghiệm; agent PR dataset cảnh báo tỷ lệ conflicts đáng kể nhưng không đo graph partition. Vì vậy ưu tiên *advisory + deterministic overlap + integration probe*; không chặn dispatch dựa một điểm rủi ro suy đoán.

### 3. Graph UI nào sống và vì sao?

Không có dữ liệu công khai đủ để xếp hạng “user quay lại tuần nào” của các code graph. Proxy thuyết phục hơn là graph có người/CI/tool tiêu thụ thường xuyên: Nx affected/task graph, GitHub dependency graph/Dependabot. View nên ưu tiên “graph của diff/run/task đang chọn”, local neighborhood và path explanation; overview toàn repo là map định hướng/onboarding tùy chọn. Cho cùng câu trả lời dạng danh sách/file/test để user không cần học canvas.

CodeSee và Sourcetrail không nên được dùng làm bằng chứng graph UX thất bại: CodeSee nêu economics và breadth/maintenance; Sourcetrail nêu maintainer interest và công duy trì. Bài học là tránh sản phẩm graph độc lập đòi parser mọi ngôn ngữ và growth path riêng; giữ scope hẹp, tận dụng dữ liệu build/test vốn có, nối graph vào action thường dùng và hiển thị stale/index status. Stars của Sourcetrail là cộng đồng quan tâm, không đủ để trả tiền cho maintenance.

### 4. Temporal coupling: hữu ích, đa ngôn ngữ, nhiều noise

Co-change chỉ cần Git paths/commit, do đó **ngôn ngữ-agnostic** và rẻ hơn semantic parsing. Nghiên cứu thực nghiệm cho thấy co-change lặp lại phản ánh structural, semantic hoặc implicit relations; age/window ảnh hưởng dự báo. Cũng có bằng chứng production/test co-evolution bị nhiễu rộng bởi việc nhiều test updates không phải test tương ứng với production file đơn giản ([study](https://doi.org/10.1145/3607183)). Vì thế dùng như tín hiệu “thường được sửa cùng”, không đổi tên thành dependency/cause.

Bộ lọc mặc định đề xuất: bỏ merge commits hoặc xử lý riêng; exclude bot/dependency bump, bulk formatting/renames/generated/vendor/lockfile; không tính commit có quá nhiều files (threshold cấu hình/robust percentile); require min pair count + support/confidence; giới hạn thời gian, giảm trọng số commit cũ; tách author/task/commit-type khi có metadata; tách code↔test và code↔config; hiển thị sample commits để giải thích; cho phép exclude path. Không có ngưỡng chuẩn phổ quát. Chạy retrospection trên chính repo và hỏi liệu các cảnh báo tìm ra “missing file” thật hay chỉ formatting trước khi bật trong manager workflow.

## Kế hoạch kiểm chứng tại Onni trước khi nâng mức cam kết

1. Tạo fixture TS monorepo có package imports, root config, barrel hub, dynamic import, subprocess CLI, generated file và test không import trực tiếp; đánh giá precision/recall theo edge type.
2. Replay các commit lịch sử của Onni và 3–5 repo khác nhau; so sánh full verify, workspace-target selection, file import selection, runner-native related tests. Đo test count, wall time, missed failures/known changed paths; không chỉ đo số tests giảm.
3. Replay 2+ branch changes đồng thời; đo exact same-file overlap, Git trial-merge conflict, build/test integration failures và co-change warning precision riêng. Báo tỉ lệ trên từng cặp, không một score tổng.
4. UI experiment: xem task/diff impact, yêu cầu người dùng trả lời “cần kiểm gì tiếp?” và “vì sao file này affected?”; đo thời gian đến đúng file/test và mở graph lại sau đó. Không suy ra retention từ stars.
5. Nếu test selection bỏ sót một failure trong validation set, giữ nó là suggestion-only và mặc định vẫn chạy full verification theo workflow hiện có.

## Bài học cho OnniCode

1. **Copy ngay: graph phải phục vụ một hành động lặp lại.** Tập trung “impact của diff/run” và candidate tests; dùng graph làm input cho query/action, không ship canvas overview đơn độc. Proven: Nx/GitHub ghép graph với CI/security action.
2. **Tận dụng authority sẵn có.** Dùng npm workspace graph + Git; gọi Nx/Turbo/Rush/Bazel/Pants và Vitest/Jest nếu repo đã dùng. Tránh reimplement build semantics. Proven qua docs/CLI behavior; effort thấp.
3. **Mặc định báo candidate có giải thích, không tuyên bố chắc chắn.** Show provenance, confidence, paths, global inputs và cap/aggregate hub impact; fallback test rộng khi graph không đủ. Proven: dynamic/runtime edges và repo config làm static selection incompleteness; false-negative cost cao.
4. **Cho manager phân vùng bằng ownership rồi thử tích hợp sớm.** Worktree per child + one owner per file/shared artifact + contract first + trial merge/test. Dùng overlap làm hard fact, co-change làm warning. Isolation không tự ngăn semantic conflicts.
5. **Thêm co-change như edge mềm, opt-in theo view.** Giữ commit provenance, time decay, min support, bulk-change/noise filters; đo usefulness trên lịch sử của repo. Có nghiên cứu cross-language và nhiều hệ thống, nhưng prediction quality/domain validity chưa phổ quát.
6. **Ưu tiên quick-win architecture checks trước đồ thị đẹp.** Cycle/orphan/unused rules tạo finding CI actionable; Knip/dependency-cruiser/Madge là đối thủ/thành phần để học hoặc gọi, nhưng benchmark ROI độc lập còn thiếu.
7. **Không dựng recommender ML kiểu Meta lúc đầu.** Meta có kết quả mạnh nhưng cần data, flaky-test handling và hạ tầng quy mô lớn; số liệu tự báo cáo trên Facebook không ngoại suy được sang local repos.
8. **Tránh hứa “dự báo conflict” dựa import graph.** Thử merge là chính xác nhất cho conflict văn bản; scope ownership giảm collision; graph/co-change chỉ ưu tiên cảnh báo. Conflict semantically incompatible có thể nằm ở file disjoint.
9. **Không dùng shutdown làm verdict UX.** CodeSee/Sourcetrail cung cấp bằng chứng về economics và maintenance; không chứng minh map vô ích. Chọn local-first, phạm vi phân tích giới hạn, adapter ecosystem và graph gắn workflow để tránh cost trap.
10. **Đo thói quen chứ không đo tò mò.** Track local-only product metrics hoặc usability study opt-in: graph-to-action success, correctness, time-to-find, repeat use; không dùng stars/downloads/LLM demo làm retention proxy.
