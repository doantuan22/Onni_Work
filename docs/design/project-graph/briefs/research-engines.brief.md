# Brief: research-engines

CONTEXT. OnniCode (this repo; read AGENTS.md first) is a local cockpit that runs AI coding-agent tasks, each in its own git worktree. The owner wants a NEW feature, separate from (not replacing) the existing "Automations": a PROJECT GRAPH - the repository represented as nodes and edges (modules, files, symbols, tests, docs, contract schema->route->client->hook chains, git co-change, agent runs touching nodes). It must (a) let users SEE and understand links inside the project visually in the cockpit, and (b) let agents query it (CLI such as onni graph neighbors/impact/path/context, with a token budget) together with the project-context layer. The graph is built and updated BY CODE (deterministic static analysis + git history, incremental by commit/content hash, cached under .ai/onni/, never required, zero-config, local-first, no upload); an LLM-written summary layer is optional, OFF by default, labelled as AI-written. Edges carry provenance (extracted/inferred/declared). It will also be used by the manager-worker system (partition scopes into disjoint regions, predict conflicts, pick tests for verify).

We are in a SURVEY + PLANNING phase: NOTHING is built yet. YOUR JOB IS RESEARCH ONLY. Do not change any file except the single markdown report named in your order. Write the report in Vietnamese prose with English identifiers/paths/URLs. Be precise and verifiable: cite file paths with symbols (grep to confirm; line numbers may be approximate), cite URLs for external facts with the date you fetched them, and mark anything you could not verify as "chua kiem". Never invent. If you lack network access or a tool, say so explicitly in the report and in your final report instead of guessing. Keep the report focused and skimmable (tables where useful), no more than about 600 lines. Commit the report on your branch with a conventional commit like docs(graph): <subject>. When done call onni task report with status, a 5-line summary, and the report path.

YOUR PART: EXTERNAL RESEARCH A - code-analysis ENGINES and AGENT-FACING repo maps. Report file: docs/design/project-graph/research-engines.md. Find and study at least 12 real, existing open-source projects/tools on GitHub (verify each one exists and is alive; give URL, license, primary language, stars and last-commit date as seen when you fetched it). Cover these families:
(a) static-analysis / index engines: TypeScript compiler API and ts-morph, tree-sitter (+ tree-sitter-graph, GitHub stack-graphs), SCIP / LSIF and Sourcegraph scip-* indexers, Kythe, universal-ctags, ast-grep, madge, dependency-cruiser, Joern or CodeQL (as heavy options), es-module-lexer/oxc/swc based import scanners;
(b) AGENT-FACING code graph / repo map tools: Aider repo-map (tree-sitter + PageRank), Repomix, code-graph-rag, CodeGraphContext, any MCP servers that expose a code graph, Continue/Cline/Cursor indexing approaches if documented, and similar "graph for LLM agents" projects you can find;
(c) git-history mining: code-maat, CodeScene-style temporal/logical coupling, git-of-theseus, and how they compute co-change.

For EACH project give: what graph model it uses (node and edge types), how it builds and how it UPDATES incrementally (or not), supported languages, scale evidence (repo sizes, speed claims, with source), output formats/storage, how an agent or UI consumes it (CLI/MCP/API), licensing fit for embedding in a commercial product, install/runtime weight (native binaries or WASM; Windows support), strengths, weaknesses, and "borrow / avoid" for our design.

Then end with: a comparison table; a recommended engine strategy for (1) a TypeScript-first MVP that must also grow to multi-language, (2) incremental update design, (3) edge-provenance model, (4) how to expose the graph to agents within a token budget (compare Aider's ranked repo map with graph-query CLIs), and (5) a list of pitfalls others hit (false edges, dynamic imports, monorepos/workspaces, generated code, huge repos, Windows paths).

Prefer primary sources (repo README, docs, source code) over blog posts; quote short snippets only when needed. If you can browse, actually open the repos; if you cannot, say so on the first line of the report and limit yourself to what you can verify locally.
