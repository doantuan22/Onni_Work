# Brief: research-viz

CONTEXT. OnniCode (this repo; read AGENTS.md first) is a local cockpit that runs AI coding-agent tasks, each in its own git worktree. The owner wants a NEW feature, separate from (not replacing) the existing "Automations": a PROJECT GRAPH - the repository represented as nodes and edges (modules, files, symbols, tests, docs, contract schema->route->client->hook chains, git co-change, agent runs touching nodes). It must (a) let users SEE and understand links inside the project visually in the cockpit, and (b) let agents query it (CLI such as onni graph neighbors/impact/path/context, with a token budget) together with the project-context layer. The graph is built and updated BY CODE (deterministic static analysis + git history, incremental by commit/content hash, cached under .ai/onni/, never required, zero-config, local-first, no upload); an LLM-written summary layer is optional, OFF by default, labelled as AI-written. Edges carry provenance (extracted/inferred/declared). It will also be used by the manager-worker system (partition scopes into disjoint regions, predict conflicts, pick tests for verify).

We are in a SURVEY + PLANNING phase: NOTHING is built yet. YOUR JOB IS RESEARCH ONLY. Do not change any file except the single markdown report named in your order. Write the report in Vietnamese prose with English identifiers/paths/URLs. Be precise and verifiable: cite file paths with symbols (grep to confirm; line numbers may be approximate), cite URLs for external facts with the date you fetched them, and mark anything you could not verify as "chua kiem". Never invent. If you lack network access or a tool, say so explicitly in the report and in your final report instead of guessing. Keep the report focused and skimmable (tables where useful), no more than about 600 lines. Commit the report on your branch with a conventional commit like docs(graph): <subject>. When done call onni task report with status, a 5-line summary, and the report path.

YOUR PART: EXTERNAL RESEARCH B - VISUALIZATION and UX products, and rendering libraries. Report file: docs/design/project-graph/research-viz.md. Find and study at least 12 real, existing products/projects (verify each exists; URL, license or pricing model, last activity as seen when you fetched it):
(a) code/architecture visualizers: CodeSee, Sourcetrail (archived OSS), Emerge, CodeCharta, Gource, Understand (SciTools), Structure101/Lattix class tools, Sourcegraph code navigation and Code Insights, GitHub dependency graph / CodeQL path views, Nx project graph and Turborepo graph (closest monorepo examples), Obsidian graph view / Logseq (UX of a knowledge graph), Neo4j Bloom or Gephi (large-graph UX), CodeScene behavioural code analysis (hotspots, change coupling); plus any "repo to graph" open-source projects for LLM agents that include a UI.
(b) rendering libraries and their real limits: @xyflow/react (React Flow), dagre, elkjs, cytoscape.js (+ fcose/cola layouts), sigma.js + graphology, d3-force, vis-network, Cosmograph/cosmos, deck.gl. Give node-count limits with evidence (benchmarks or maintainer statements, cite sources), layout cost, clustering/compound-node support, accessibility, React integration, bundle size, license.

For EACH product give: nodes/edges shown, zoom/aggregation strategy (semantic zoom, collapsing, level-of-detail), filters, overlays (churn/heatmap/ownership/coverage), time travel, search, how selection/side panels work, impact-analysis UX, how it handles very large graphs, what users praise or complain about (cite), and "borrow / avoid" for a cockpit that already uses @xyflow/react + dagre.

Then end with: comparison tables (products; libraries); a recommended rendering strategy for repo-scale graphs (say at which node counts to switch from xyflow to a canvas/WebGL renderer, and whether to cluster server-side); a recommended UX spec outline (default view, zoom levels, filter set, overlay set, side panel contents, "show impact of this diff", "start a task here", live "worker is editing this node" highlight, empty/error/loading states, keyboard and accessibility); and a list of UX anti-patterns ("hairball" graphs etc.) with how others avoid them.

Prefer primary sources (official docs, repos, benchmarks). If you can browse, actually open the pages; if you cannot, say so on the first line of the report and limit yourself to what you can verify locally (the repo already has @xyflow/react and @dagrejs/dagre in packages/web/package.json and an activity graph under packages/web/src/routes/workflow-graph).
